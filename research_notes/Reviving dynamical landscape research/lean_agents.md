# Lean interoperability and agentic scientific coding (as of 2026-10-19)

Scope: Julia multiple dispatch / two-language claims for coding agents vs Python/Rust; Lean FFI bindings (C ABI, Rust, Python, Julia); proof artifact/certificate checking; Mathlib ODE/PDE/dynamical-systems/verified-numerics maturity; soundness vs numerical validation; small first formalization + equal-budget agent benchmark for the bifurcation / periodic-orbit / PDE-pattern / landscape-map program. All web sources accessed 2026-10-19.

Review provenance (2026-10-19): selective single-round source audit; original research citations retained. Corrections and remaining limits are recorded in `audit.md`. No Lean build or library soundness audit was performed.

## Key Question 1: Does Julia multiple dispatch / the two-language solution demonstrably improve agent productivity or bug surface vs Python/Rust?

### Takeaway
Not established by the sources reviewed here. The three named repair/editing benchmarks do not include Julia; that is a search-limited result, not proof that no Julia-agent study exists. Their heterogeneous tasks and repositories do not isolate a causal language effect. Julia's dispatch/productivity advantage remains a hypothesis to test.

### Cited Findings
- Julia's "two-language problem" claim originates as a design rationale by the language authors — "Julia: A Fresh Approach to Numerical Computing" (Bezanson, Edelman, Karpinski, Shah, SIAM Review 2017) — a position/design paper with no agent or defect-rate measurements — [arXiv 1411.1607](https://arxiv.org/abs/1411.1607).
- SWE-bench Multilingual (Khandpur, Lieret, Jimenez, Press, Yang; 2025): 300 tasks, 42 repos, 9 languages (C, C++, Go, Java, JavaScript, TypeScript, PHP, Ruby, Rust — Python tasks excluded; Python compared via SWE-bench Verified). SWE-agent + Claude 3.7 Sonnet resolved 43% on Multilingual vs 63% on SWE-bench Verified (Python) at a fixed $2.50/task cost cap; per-language: Rust highest 58.14%, Java 53.49%, PHP 48.84%, Ruby 43.18%, JS/TS 34.88%, Go 30.95%, C/C++ lowest 28.57%. Authors state "it's hard to say what factors are most important" and note single-model and small-patch (median 10 LOC) limitations — [SWE-bench Multilingual](https://www.swebench.com/multilingual.html).
- The authors note Python-specific assumptions in agent frameworks; this is a tooling observation, not a measured causal explanation of the score gap — [SWE-bench Multilingual](https://www.swebench.com/multilingual.html).
- Multi-SWE-bench (Zan et al., 2025; NeurIPS 2025): 1,632 issue-resolving instances across 8 languages (Python, Java, TypeScript, JavaScript, Go, Rust, C, C++), evaluated with both procedural and agent-based frameworks — no Julia — [arXiv 2504.02605](https://arxiv.org/html/2504.02605v1), [site](https://multi-swe-bench.github.io/).
- Aider polyglot benchmark (Gauthier, 2024-12-21): 225 hardest Exercism exercises in 6 languages (C++, Go, Java, JavaScript, Python, Rust); measures LLM code-editing (correct diff applied), not agentic repo repair; top score o1-2024-12-17 (high) 61.7% — no Julia — [aider blog](https://aider.chat/2024/12/21/polyglot.html), [leaderboard](https://aider.chat/docs/leaderboards/).
- MultiPL-E (Feder et al., 2022) is the main multi-language *code-generation* benchmark that includes Julia, and reports per-language pass-rate differences (Python historically strongest); no agentic/repair setting — [arXiv 2208.08227](https://arxiv.org/abs/2208.08227).

### Inferences
- Evidence classification: (a) *empirical, agentic*: 43% and 63% are scores on different datasets, not a matched-language experiment; they establish neither Python superiority nor its cause. Rust ranks highest within the reported Multilingual run. (b) *non-agentic*: MultiPL-E measures code generation, not repository repair. (c) *untested here*: Julia dispatch or removal of language boundaries may affect agent productivity and defects, but no direct measurement was identified in this search.
- Plausible pro-Julia design arguments (untested): no prototype→rewrite step reduces total agent task complexity in scientific computing; `MethodError` with candidate-method listings gives more actionable feedback than duck-typed Python failures; one implementation language reduces the API-drift class of bugs between prototype and production numerics.
- Plausible anti-Julia design arguments (untested): training-data coverage and harness support could affect performance. The score gap does not measure Julia training-data scarcity or predict the size or direction of a Julia effect.
- Bug surface: no dispatch-specific agent-defect measurement was identified in this search. Rust's reported resolve rate does not isolate compiler feedback as its cause.

### Gaps
- Julia is absent from the three named repair/editing benchmark datasets; coverage of all existing studies was not established. A matched-task, equal-budget experiment would address the specific Julia-vs-Python/Rust claim better than cross-dataset scores (see Key Question 4).
- Multi-SWE-bench's per-language resolve rates were not extracted this session; I could not verify whether its language ranking agrees with SWE-bench Multilingual's (Rust-highest). Cross-benchmark language rankings should not be treated as stable without checking both.
- MultiPL-E's specific Julia pass@1 numbers were not re-verified; Julia static-analysis tooling for agent self-checking (e.g. JET.jl) was not evaluated here.

## Key Question 2: Which stack complements Lean? Verified status of FFI / bindings (C ABI, Rust, Python, Julia) and proof artifact/certificate checking

### Takeaway
Lean's documented interop boundary is the C ABI (`@[extern]`/`@[export]` over `lean.h`, explicitly unstable), not a formally verified boundary. Python and Rust have the cited integrations; no maintained Julia↔Lean binding was found in the original search. Axiom inspection, kernel replay and independent checking address different trust risks; they are not a single automatic certification ladder.

### Cited Findings
- Lean Language Reference §12.4 Foreign Function Interface (current, lean-lang.org): "Lean offers efficient interoperability with any language that supports the C ABI"; Lean ABI is based on the platform's standard C calling convention; `@[extern "sym"]` binds C symbols, `@[export sym]` exposes Lean to C; type translation table (uint8..uint64/size_t; `Char`→`uint32_t`; `Float`→`double`; `Nat`/`Int`→`lean_object *` with scalar unboxing; other inductives as `lean_object *`); borrowing annotation `@&`; required module initializers (`initialize_foo_A_B`, `lean_setup_args`, `lean_initialize_thread`); interpreter support via `--load-dynlib`. Explicit limitations: "designed for internal use in Lean and should be considered unstable", and no compound C `struct`s by value across the boundary — [Lean reference, FFI](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Foreign-Function-Interface/). Official FFI and reverse-FFI examples live in the Lean repo — [ffi examples](https://github.com/leanprover/lean4/tree/master/tests/lake/examples/ffi).
- Rust↔Lean: `argumentcomputer/lean-ffi` — "A Rust library that wraps low-level bindings to the lean.h Lean C library with a high-level API for safe and ergonomic FFI from Lean to Rust" — [GitHub](https://github.com/argumentcomputer/lean-ffi). Independent precedent: calling Lean from Rust via `bindgen` on `<lean/lean.h>` (Aniva, 2024-03-04) — [Trillium devlog](https://leni.sh/post/240304-rust-call-lean/). Community position that auto-generating a Rust C-FFI layer for arbitrary Lean files is feasible — [Lean4 Zulip archive](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/FFI.20to.20Rust.2FC.2B.2B.html).
- Python↔Lean (agent-facing): Pantograph (Aniva, Sun, Miranda, Barrett, Koyejo; arXiv 2410.16429, v1 2024-10-21, v2 2025-01-31) — machine-to-machine interface to Lean 4 enabling MCTS proof search, proof-sketch workflows, and data extraction — [arXiv](https://arxiv.org/abs/2410.16429), [repo (leanprover mirror)](https://github.com/leanprover/Pantograph); PyPantograph (Python bindings to Pantograph) referenced in practice discussions — [Proof Assistants SE](https://proofassistants.stackexchange.com/questions/5020/why-use-tree-sitter-lean-or-pypantograph-to-extract-lean-4-constructs-like-eval). LeanDojo — Lean theorem-proving environment for ML supporting whole-proof generation and interactive proof search — [leandojo.org](https://leandojo.org/leandojo.html).
- Julia↔Lean: no maintained binding surfaced in web searches (2026-10-19); the documented C-ABI boundary means a `ccall`-based bridge to `lean.h` is technically possible but would be bespoke, unverified work.
- Proof artifact/certificate checking ladder (Lean Language Reference, "Validating a Lean Proof", current): (1) blue double-check marks / `lake build` (kernel acceptance); (2) `#print axioms` — flags `sorryAx`, custom axioms, and native-computation axioms; (3) `lean4checker` — replays stored `.olean` declarations through the kernel; trusts olean structural validity; prone to crafted-olean attacks; recommended as CI via `lean-action` (`lean4checker: true`) — [reference](https://lean-lang.org/doc/reference/latest/ValidatingProofs/), [leanprover/lean4checker (README updated 2026-03-25)](https://github.com/leanprover/lean4checker); (4) gold standard `lake comparator` — sandboxed build, serialized proof-term export, replay by Lean kernel and/or external checkers, with statement-matching against a trusted challenge file; supports `nanoda`, an independently developed Rust checker; more external checkers listed at the Lean Kernel Arena — [reference](https://lean-lang.org/doc/reference/latest/ValidatingProofs/), [nanoda_lib](https://github.com/ammkrn/nanoda_lib), [arena](https://arena.lean-lang.org/). Lean4Lean (Carneiro et al.) — first complete external typechecker for Lean 4, written in Lean — [arXiv 2403.14064 (v3 2025-09-14)](https://arxiv.org/html/2403.14064v3).
- Version-dependent native trust: through 4.28, native proofs used `Lean.trustCompiler`; since 4.29, native computations introduce dedicated axioms. Lean 4.35.0 (released 2026-10-12) removed the old reduction machinery, **not native evaluation or its additional trust**. An external checker may check a derivation conditional on a native axiom without validating that computation. Pin the toolchain and inspect actual axioms; do not generalize the historical external-checker limitation to every version — [reference](https://lean-lang.org/doc/reference/latest/ValidatingProofs/), [4.35.0 release notes, #14953](https://lean-lang.org/doc/reference/latest/releases/v4.35.0/).

### Inferences
- Proposed integration: keep numerics outside the proof process and pass bounded data/certificates through a checked interface. This avoids making the numerical implementation a logical premise, but still requires parser, statement and process-isolation review; FFI code can compromise the process even when it is not a logical axiom.
- Distinguish certificate generation from its verification. Kernel-reducible checking avoids trusting native computation of the result; native-asserted results retain additional assumptions under the pinned version's axiom policy. Neither path is literally trust-free. See the version-specific finding above.
- Numerical certificate support is not absent: LeanCert advertises checked bounds, roots and integration, separate from proof-term export. Its suitability and dependency axioms for this project remain to be audited — [LeanCert](https://github.com/alerad/leancert).

### Gaps
- Julia↔Lean: absence of a binding is a negative search result, not an exhaustive registry audit; nothing found on JuliaHub/GitHub via search.
- LeanDojo's currently supported Lean/Mathlib versions (historically pinned, lagging HEAD) were not verified this session — check before building an agent pipeline on it.
- Pantograph/PyPantograph API stability and current Mathlib compatibility not reviewed in detail; comparator's serialized export format internals not reviewed.
- Platform caveat: Lean 4.35 release notes describe the integrated checking sandbox as Linux-only; do not assume the same isolation is available on this macOS host. Default `lake check` rejects nonstandard axioms, including native-computation assumptions — [4.35.0 release notes](https://lean-lang.org/doc/reference/latest/releases/v4.35.0/).
- Sage↔Lean bridges (e.g. sagelean) not verified within budget.

## Key Question 3: Mathlib maturity for ODEs, PDEs, dynamical systems, verified numerics; soundness vs numerical validation

### Takeaway
The six-file ODE-directory inventory is not an inventory of Mathlib or the Lean ecosystem. Flows/invariant sets and distribution/Fourier machinery live elsewhere, and external interval libraries exist. No ready-made, end-to-end certified bifurcation/periodic-orbit/PDE pipeline was verified here. Mathematical certification by validated numerics and formal checking in Lean are distinct guarantees; neither should be confused with ordinary numerical testing.

### Cited Findings
- `Mathlib/Analysis/ODE` on master (fetched 2026-10-19) contains exactly: `Basic.lean`, `DiscreteGronwall.lean`, `ExistUnique.lean`, `Gronwall.lean`, `PicardLindelof.lean`, `Transform.lean` — i.e. ODE well-posedness (Picard–Lindelöf existence/uniqueness) and Grönwall inequalities in continuous and discrete form; no Euler/scheme verification, no linear-ODE/Floquet theory, no stability or bifurcation theory, no Poincaré-map machinery in this directory — [mathlib4 tree](https://github.com/leanprover-community/mathlib4/tree/master/Mathlib/Analysis/ODE).
- Lean's `Float` is the FFI-facing double (`Float`→`double` per the ABI table); Mathlib's analysis is built on `Real`; the FFI reference documents the `Float`-to-C mapping but no formal `Float`↔`ℝ` soundness bridge — [Lean reference, FFI](https://lean-lang.org/doc/reference/latest/Run-Time-Code/Foreign-Function-Interface/).
- Native evaluation remains an additional trust boundary after removal of the historical machinery; apply the version-specific distinctions in Key Question 2 — [4.35.0 release notes](https://lean-lang.org/doc/reference/latest/releases/v4.35.0/).
- Beyond the ODE folder, Mathlib defines flows and invariant sets in `Dynamics/Flow.lean`, and tempered distributions, directional derivatives and Fourier transforms in `Analysis/Distribution/TemperedDistribution.lean`. These are reusable foundations, not evidence of a complete PDE solver/certifier — [Flow source](https://raw.githubusercontent.com/leanprover-community/mathlib4/master/Mathlib/Dynamics/Flow.lean), [TemperedDistribution source](https://raw.githubusercontent.com/leanprover-community/mathlib4/master/Mathlib/Analysis/Distribution/TemperedDistribution.lean).
- External verified numerics: LeanCert documents rational/dyadic/affine intervals and checked numerical certificates, with separate native/kernel trust qualifications. This contradicts ecosystem-wide absence, but README claims are not an independent soundness or scalability audit — [LeanCert](https://github.com/alerad/leancert).
- Independent external checkers exist for the artifact side: lean4checker (olean replay, kernel-level), nanoda (independent Rust implementation), comparator (sandbox + serialized export + multi-checker replay), Lean4Lean (complete typechecker written in Lean) — sources as cited in Key Question 2.

### Inferences
- Directly usable for the user's program: Picard–Lindelöf (continuous-time well-posedness for bifurcation-model ODEs), `DiscreteGronwall` (stability/contraction bounds for iterated maps — the natural Lean-side tool for 1D-map and periodic-orbit candidate analysis), `Transform` (ODE transformations).
- Unverified coverage is not absence: this pass does not establish whether reusable Floquet, return-map, center-manifold, bifurcation or weak-solution developments exist elsewhere. Inspect theorem statements and external projects before budgeting a from-scratch development or declaring a cheapest verification route.
- Validated enclosures plus a suitable mathematical theorem can constitute a computer-assisted proof without Lean. To claim a **Lean-checked** result additionally requires a checked encoding and proof of the relevant certificate semantics. Merely checking a list of intervals does not prove orbit existence, stability or PDE truncation control. Native-computation assumptions must be disclosed rather than treated as either invisible or universally forbidden.
- `Real`-based Mathlib statements about ODE solutions are compatible with the user's landscape-map goals at the qualitative level (existence, uniqueness, continuous dependence, attracting sets), but quantitative floating-point claims require the certificate pattern.

### Gaps
- Full `Mathlib/Dynamics` and PDE-adjacent coverage remains unreviewed; the source examples above refute extrapolation from the ODE directory alone.
- External interval-library trust, supported operations, versions and performance require a pinned-code audit; discovery of LeanCert is not evidence that it certifies this project's desired dynamical objects.
- Comparative verified-numerics maturity in other proof assistants (Isabelle/HOL's verified ODE enclosures à la Immler; CoqInterval certificate checking) is prior-literature knowledge, not re-verified this session — relevant as an alternative if Lean-side verified numerics proves too immature, but needs fresh sourcing.
- Contents of the six ODE modules were verified by filename only; theorem-level inventory not extracted.

## Key Question 4: Credible small first formalization and an equal-budget agent benchmark for the revived bifurcation / periodic-orbit / PDE-pattern / landscape program

### Takeaway
A proposed first formalization is a small map-level theorem with explicit assumptions and checked dependencies. A proposed agent evaluation uses matched scientific tasks in Python/Julia/Rust; Lean proof tasks should be a separate evaluation track, not scored as equivalent code-repair tasks. These are project proposals, not established novelty claims.

### Cited Findings
- Equal-budget protocol precedent: SWE-bench Multilingual ran one model (Claude 3.7 Sonnet) with SWE-agent under a fixed $2.50/task cost cap and reports per-language resolution rates — the citable template for "equal budget" — [SWE-bench Multilingual](https://www.swebench.com/multilingual.html).
- Agent↔Lean interface precedent: Pantograph's machine-to-machine interface with MCTS proof search and proof sketches (arXiv 2410.16429, 2024–2025); LeanDojo for whole-proof generation and interactive search — [arXiv](https://arxiv.org/abs/2410.16429), [leandojo.org](https://leandojo.org/leandojo.html).
- CI-side artifact validation: lean-action supports `lean4checker: true` (olean recheck in CI); comparator adds sandboxed build + serialized export + external checkers (nanoda) and is the manual's recommended standard for unreviewed/AI-generated proofs — [Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/), [lean4checker](https://github.com/leanprover/lean4checker).
- Mathlib assets available as foundations (verified inventory, Key Question 3): `PicardLindelof`/`ExistUnique`, `Gronwall`, `DiscreteGronwall` — [mathlib4 ODE tree](https://github.com/leanprover-community/mathlib4/tree/master/Mathlib/Analysis/ODE).
- No existing cross-language agent benchmark for scientific-computing/dynamical-systems tasks and no Julia-inclusive agentic benchmark were found (Key Question 1 findings).

### Inferences (design proposals — not literature)
- Small first formalization candidates, tentatively ordered by risk (kernel-only completion is a goal, not demonstrated here):
  1. *Logistic-map fixed point*: prove that for the map x↦r·x·(1−x) on ℝ with 1<r<3, the fixed point x*=1−1/r exists and attracts a suitable orbit neighborhood — uses only Mathlib real analysis, derivatives, and `Tendsto` machinery; directly bifurcation-adjacent (the r=3 flip bifurcation is the next milestone).
  2. *Discrete-Grönwall contraction bound*: extend `DiscreteGronwall` to a stability estimate for an iterated Lipschitz 1D map (error propagation over an orbit segment) — the certificate-side backbone for periodic-orbit claims.
  3. *Exact rational certificate check*: generate bounds for a polynomial map externally, then prove the certificate's semantic implication and check its inequalities. Start with finite-step enclosure; orbit existence or attraction requires an additional theorem. Evaluate existing interval infrastructure before implementing a new checker.
- Proposed agent benchmark: matched Python/Julia/Rust scientific tasks, fixed model and disclosed cost/token/turn caps, hidden correctness tests and repeated seeds. Record setup, execution, total time and failure types separately. A separate Lean proof track measures statement correctness, proof acceptance and allowed axioms; `#print axioms` is inspection, not itself a proof checker. A cross-language experiment tests the whole stack; isolating multiple dispatch additionally requires an ablation within Julia and cannot be inferred from language labels alone.
- Scope proposal: start with a small map-level property and a certificate with explicit semantics. The ODE folder alone does not justify a PDE feasibility estimate. For a PDE claim, distinguish the discretized system from the continuum and account for truncation and boundary conditions.
- Tooling note: the Lean-side agent stack should assume the FFI is "unstable" (documented) and keep the numerics boundary at the process level (Python/Rust process ↔ Lean via Pantograph/lean-ffi) rather than deep in-process extern coupling, until the ABI stabilizes.

### Gaps
- No effort/feasibility estimate exists for the logistic-map milestone (no published comparable formalization found this session); treat as a 1–3 agent-session pilot to be measured, not assumed.
- No existing benchmark suite for agent dynamical-systems coding was found; the proposed task suite must be built and validated (gold patches, hidden tests) from scratch, following SWE-bench Multilingual's construction/validation procedure.
- The now-identified dynamics foundations and external interval libraries may change milestone scope; theorem-level reuse has not been evaluated.
- Multi-SWE-bench per-language numbers and newer runs were not extracted. Report scores with their dataset/model/harness, not a causal or universal language ranking.
