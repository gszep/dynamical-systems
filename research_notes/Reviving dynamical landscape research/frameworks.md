# Interactive dynamical landscape software: architecture options (Julia BifurcationKit/SciML, Python JAX/PyTorch, Rust wgpu/WebGPU)

Scope note: research-only pass, 2026-10-19. No benchmarks were run, no code installed, and no connection made to the user's remote GPU host (`ssh artemis`) per assignment constraints. All performance-adjacent statements below are sourced capability/status claims; where evidence is missing it is flagged in Gaps. Proposed evaluation is a set of controlled benchmark gates, not a stack winner.

Review provenance (2026-10-19): selective single-round audit corrected deployment/precision overstatements; see `audit.md`. Browser GPU shaders, browser CPU WebAssembly and native CPU/GPU execution are separate targets.

## Key Question 1: Julia stack (BifurcationKit.jl / SciML, CUDA) — coverage of f64, sparse solvers, eigensolvers, matrix-free Newton-Krylov, AD, continuation, Floquet; maturity and deployment

### Takeaway
BifurcationKit.jl's surveyed documentation covers the requested continuation and stability methods, including large GPU examples; this is a capability inventory, not independent production validation. A native Julia backend is the conservative deployment for this full stack. Julia-generated static browser views and experimental Julia-to-Wasm computation also exist; neither demonstrates a browser port of the complete BifurcationKit/SciML stack.

### Cited Findings
- BifurcationKit.jl targets "automatic bifurcation analysis of large-scale equations F(u, λ)=0 … leverages iterative methods, dense/sparse formulations, and specialized hardware (e.g., GPUs)"; key features list PALC, deflated continuation, Newton-Krylov, "matrix-free, dense, and sparse eigensolvers", periodic orbits via shooting/finite-differences/collocation, CPU and GPU support — [BifurcationKit docs (sciml.ai)](https://docs.sciml.ai/BifurcationKit/dev/)
- The package's design avoids requiring `u <: AbstractArray`, enabling KrylovKit.jl-based (matrix-free) linear solvers — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/); [KrylovKit.jl docs](https://jutho.github.io/KrylovKit.jl/stable/#Package-features-and-alternatives-1)
- Original paper: "A Newton-Krylov method is then used to correct this predictor and a Matrix-Free eigensolver is used to compute stability and bifurcation points" — [Veltz, HAL hal-02902346](https://inria.hal.science/hal-02902346/)
- Docs table of contents (fetched 2026-10-19) includes: Krylov-Newton algorithm, linear-solver and eigensolver options pages, PALC/Moore-Penrose/ANM/deflated continuation, codim-2 fold/Hopf continuation, codim-3 Bogdanov-Takens, periodic-orbit bifurcation detection, period-doubling and Neimark-Sacker continuation, normal forms, branch switching, automatic bifurcation diagrams, event handling — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/)
- Period-doubling and Neimark-Sacker detection/continuation presuppose Floquet-multiplier computation for periodic orbits; the package claims to be "one of the few software packages that provides shooting methods alongside finite difference and collocation methods" for periodic orbits — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/) (exact Floquet-multiplier API not re-verified per-page; see Gaps)
- Documented scale claim: "used for massive computations (millions of unknowns), on the GPU", citing [arXiv:2508.19134](https://doi.org/10.48550/arXiv.2508.19134) and a [CR Math article](https://comptes-rendus.academie-sciences.fr/mathematique/item/CRMATH_2022__360_G1_59_0/) — capability claim from primary docs; no throughput numbers verified here
- Surrounding SciML ecosystem (same docs site, fetched): LinearSolve.jl, NonlinearSolve.jl, DifferentialEquations.jl, SciMLSensitivity.jl, ModelingToolkit.jl, DiffEqGPU.jl, PETScDiffEq.jl; "Third-Party Differentiation Tooling" lists SparseDiffTools.jl and FiniteDiff.jl; JuliaHub sells commercial support for ModelingToolkit/SciML — [SciML docs hub](https://docs.sciml.ai/BifurcationKit/dev/)
- BifurcationKit itself enumerates the competition: AUTO-07p, XPPAUT, MATCONT, PyDSTool, COCO, pde2path, Trilinos-LOCA, CL_MATCONTL, python packages pyNCT, pacopy, defcont (Farrell); Julia alternatives HomotopyContinuation.jl, NumericalContinuation.jl (Barton), and unmaintained Bifurcations.jl — [BifurcationKit docs, "Other software"](https://docs.sciml.ai/BifurcationKit/dev/)
- Docs reproducibility block: BifurcationKit v0.4.17, built 2026-10-03 with Julia 1.10.12 — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/)

### Inferences
- For dynamical-landscape work needing continuation + stability + GPU scale in one coherent language, the Julia stack has the least capability risk of the three: the exact algorithmic chain the assignment names (matrix-free Newton-Krylov corrector, matrix-free eigensolver stability, arclength continuation, Floquet-type PO analysis) is BifurcationKit's documented core design, not an assembly of separate libraries.
- Browser deployment has several levels: WGLMakie/Bonito can export views with selected client-side interactions without a live Julia process; arbitrary Julia callbacks need a runtime/backend. Experimental WebAssemblyCompiler compiles a restricted, type-stable Julia subset without dynamic dispatch or BLAS/C dependencies. It was not tested for BifurcationKit compatibility — [WGLMakie](https://docs.makie.org/stable/explanations/backends/wglmakie), [WebAssemblyCompiler](https://tshort.github.io/WebAssemblyCompiler.jl/).
- GPU support alone does not establish f64 support for every operation, equal CPU/GPU numerical semantics, or useful double-precision throughput. Verify device, backend, dtype and solver coverage before making those claims; the original CUDA.jl coverage gap below remains.

### Gaps
- BifurcationKit.jl's LICENSE (widely expected permissive/MIT) was not verified against the repo this session.
- Exact Floquet-multiplier API/limitations in BifurcationKit (e.g., for large sparse PO problems) not re-verified against its periodic-orbit pages; inferred from capability listing above.
- Static WGLMakie interactivity and experimental Julia-to-Wasm routes are now source-identified, not benchmarked. Static export is not equivalent to executing arbitrary Julia callbacks or to compiling the full numerical stack.
- CUDA.jl float64 support and sparse-GPU specifics were not directly verified against CUDA.jl docs; only BifurcationKit's "GPU support" statements and the cited million-unknowns papers were sourced.

## Key Question 2: Python stack (JAX, PyTorch, scipy ecosystem) — same capability checklist, continuation/Floquet landscape, and browser story

### Takeaway
Python combines AD/GPU libraries with separate continuation machinery such as AUTO-07p. The cited sources do not establish a supported browser deployment of this complete scientific stack; this is narrower than saying no JAX/PyTorch-derived computation can ever run in a browser. Pyodide package availability and experimental inference exports must be checked separately. Sparse-GPU performance remains workload-specific rather than a universal language limitation.

### Cited Findings
- JAX defaults to 32-bit (`jax_enable_x64=False` blocks float64 creation entirely, truncating to f32 with a warning); enabling `jax.config.update('jax_enable_x64', True)` or `JAX_ENABLE_X64=1` gives f64; recommended as a global setting, with a sparingly-used `jax.enable_x64()` context manager — [JAX docs: Default dtypes and the X64 flag](https://docs.jax.dev/en/latest/101/default_dtypes.html)
- Rationale for the f32 default is the AI/GPU user base; f32 is "standard for GPU computing" — [QuantEcon JAX intro](https://jax.quantecon.org/jax_intro.html)
- JAX = NumPy-like API combining automatic differentiation and the XLA compiler; same code across CPU/GPU/TPU — [AMD ROCm JAX compatibility docs](https://rocm.docs.amd.com/en/docs-6.3.1/compatibility/ml-compatibility/jax-compatibility.html)
- Sparse-on-GPU weakness: user-reported CPU-vs-GPU sparse slowdown — [jax#8531 discussion](https://github.com/jax-ml/jax/discussions/8531); "performing robust and efficient sparse linear algebra on GPUs remains a practical bottleneck in many JAX-based workflows" — [JAX-AMG paper (arXiv 2606.09001)](https://arxiv.org/html/2606.09001v1)
- Newton-Krylov-class tools: Optimistix provides root finding, minimisation, fixed points, least squares in JAX — [Optimistix GitHub](https://github.com/patrick-kidger/optimistix); [Optimistix paper (arXiv 2402.09983)](https://arxiv.org/html/2402.09983v1); its root-find uses `lineax.linear_solve` by default — [Optimistix root-find example](https://docs.kidger.site/optimistix/examples/root_find/); lineax is "a JAX library for linear solves and linear least squares" — [lineax on PyPI](https://pypi.org/project/lineax/); Optimistix solvers are fully differentiable — [Kitchingroup tutorial](https://kitchingroup.cheme.cmu.edu/differentiable-flowsheets/jax-tutorials/10_optimistix_solvers.html)
- PyTorch (2.14 docs, updated May 2026) supports float64 as default dtype via `torch.set_default_dtype` — [PyTorch docs](https://docs.pytorch.org/docs/stable/generated/torch.set_default_dtype.html); PyTorch maintains a numerical-accuracy note — [PyTorch docs](https://docs.pytorch.org/docs/stable/notes/numerical_accuracy.html); CPU paths "often use double precision (float64) … which provides more accuracy" in a CPU-vs-CUDA result-difference thread — [pytorch#116966](https://github.com/pytorch/pytorch/issues/116966); CUDA hardware itself supports double precision — [Stack Overflow canonical answer](https://stackoverflow.com/questions/2816992/double-precision-floating-point-in-cuda)
- Apple-MPS PyTorch backend reportedly lacks float64 GPU compute (community report) — [Apple developer thread](https://discussions.apple.com/thread/256120698)
- Continuation/bifurcation in Python is wrapper-based: AUTO-07p is "publicly available software for continuation and bifurcation problems in ordinary differential equations originally written in 1980" — [auto-07p GitHub](https://github.com/auto-07p/auto-07p); pycobi wraps it — [pycobi on PyPI](https://pypi.org/project/pycobi/); auto-AUTO automates AUTO runs and bifurcation-point tracking (JOSS 2025) — [JOSS paper](https://joss.theoj.org/papers/10.21105/joss.08079.pdf); pure-Python options pacopy, pyNCT, defcont are enumerated in BifurcationKit's comparison list — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/)
- Browser compute: Pyodide compiles CPython to WebAssembly to "run full Python directly in the browser without servers or installations" — [The New Stack](https://thenewstack.io/run-real-python-in-browsers-with-pyodide-and-webassembly/); Pyodide does not support threading/multiprocessing — [Pyodide docs](https://pyodide.org/en/stable/usage/wasm-constraints.html); as of March 2026 Pyodide supports only up to Python 3.13 — [ericmjl blog](https://ericmjl.github.io/blog/2026/3/8/my-weekend-experiment-pymc-wasm/)
- The cited issues concern jaxlib/Pyodide support and mention IREE as a separate route; they do not establish impossibility of all JAX-derived browser execution. A supported deployment for this full numerical workload was not verified here — [jax#1472](https://github.com/jax-ml/jax/issues/1472), [pyodide-recipes#187](https://github.com/pyodide/pyodide-recipes/issues/187).

### Inferences
- The Python stack reaches the full checklist only as an assembly: JAX/PyTorch for AD + f64 GPU arrays, Optimistix/lineax for Newton-type solves, scipy/CPU for sparse and eigenvalue work (scipy specifics not re-verified; see Gaps), and AUTO-07p via wrappers for continuation/Floquet. Each seam (wrapper overhead, f32/f64 discipline, CPU↔GPU data movement, sparse-GPU bottlenecks) is a place where correctness or performance assumptions must be tested rather than assumed.
- Proposed low-risk deployment for the surveyed Python scientific stack: run its heavy numerics natively and share results via a browser UI. This is not a proof that all such computations require a server; package ports and restricted compiled/inference exports have different capabilities, not reviewed here.
- JAX's x64 flag being global-but-opt-in is a known footgun for landscape work (silent f32 truncation if the flag is missed) — a correctness gate (compare against a float64 CPU reference) belongs in any evaluation.

### Gaps
- scipy.optimize.newton_krylov and scipy.sparse.linalg/ARPACK eigensolver coverage (and their CPU-only scope) were not re-verified against scipy docs this session; treat as long-standing CPU features pending confirmation.
- JAX GPU eigensolver coverage (e.g., jnp.linalg.eigh on GPU; any sparse/matrix-free eigensolver equivalent) was not verified.
- Whether Optimistix/lineax offer Krylov (matrix-free iterative) linear solves suitable for large-scale Newton-Krylov was not verified beyond "linear solves and linear least squares".
- PyTorch-in-browser status (experimental wasm inference builds) not verified.
- Pyodide distribution download size (transfer cost) not verified.
- AUTO-07p license terms not verified (repo describes itself as "publicly available software"); pycobi/auto-AUTO license terms not verified.
- Exact Floquet-multiplier workflow in AUTO-07p (via pycobi) not re-verified against the AUTO manual this session; AUTO's periodic-orbit continuation reputation is the basis, per [AUTO-07p manual/tutorial PDF](https://depts.washington.edu/bdecon/workshop2012/auto-tutorial/documentation/auto07p%20manual.pdf).

## Key Question 3: Rust + wgpu/wasm/WebGPU (+ native CUDA) — f64 in the browser, browser limits and transfer costs, licensing, ecosystem maturity

### Takeaway
Rust/wgpu is a candidate portable explorer, not a measured winner. **Rust native CPU and browser WebAssembly CPU code can use f64; portable WebGPU/WGSL GPU shaders have no concrete f64 type.** WGSL has f32 and optional f16 floating-point execution (and integer types); this restriction is not a browser-wide precision ceiling. WebGPU buffer limits constrain GPU resources, not all CPU/Wasm state — [WebAssembly numeric types](https://webassembly.github.io/spec/core/syntax/types.html), [WGSL types](https://www.w3.org/TR/WGSL/#scalar-types).

### Cited Findings
- wgpu is "a cross-platform, safe, pure-Rust graphics API … runs natively on Vulkan, Metal, D3D12, and OpenGL; and on top of WebGL2 and WebGPU on wasm"; it is the core of WebGPU integration in Firefox, Servo and Deno; repository states "Apache-2.0, MIT licenses found"; current release v30 with MSRV 1.87; on wasm (without the "webgl" feature) WGSL shaders pass through to the browser's own WebGPU implementation — [wgpu GitHub README](https://github.com/gfx-rs/wgpu)
- wgpu's supported-platforms table lists Vulkan/Metal/DX12/OpenGL/WebGPU-on-wasm — no CUDA backend — [wgpu README](https://github.com/gfx-rs/wgpu)
- WebGPU availability as of early Oct 2026 (wiki edited 2026-10-02): Chromium stable on Windows/Mac/ChromeOS since 113, Android since 121, Linux Intel since 144 and NVIDIA (Wayland, driver 535.183.01+) since 147; Firefox stable on Windows (141) and macOS (145/147), Linux/Android Nightly with stable expected during 2026; Safari 26 on macOS/iOS/visionOS; Firefox and Servo implement WebGPU on top of wgpu — [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- WGSL float64: open feature request "Double precision floats (IEEE-754 binary64)" (issue #2805) asking for an f64 type; per community/expert discussion the issue "is still being discussed in the spec. For now, there's no way to tell WebGPU/WGSL that you prefer precision over speed" — [gpuweb#2805](https://github.com/gpuweb/gpuweb/issues/2805); [Stack Overflow: 2Sum in WGSL](https://stackoverflow.com/questions/78282229/why-the-2sum-algorithm-in-wgsl-doesnt-work). Half precision (shader-f16) did ship, e.g. Chrome 120 — [Chrome blog](https://developer.chrome.com/blog/new-in-webgpu-120)
- WebGPU limit defaults: maxStorageBufferBindingSize max 134217728 bytes (128 MiB) per the spec — [W3C WebGPU spec](https://www.w3.org/TR/webgpu/); wgpu docs: "Maximum size in bytes of a binding to a storage buffer. Defaults to 128 MiB" — [wgpu Limits (docs.rs)](https://docs.rs/wgpu/latest/wgpu/struct.Limits.html); default maxBufferSize is 256 MiB — [three.js#29865](https://github.com/mrdoob/three.js/issues/29865); devices can request higher adapter limits, e.g. an adapter reporting maxBufferSize 4294967296 via requiredLimits — [Chrome blog (133)](https://developer.chrome.com/blog/new-in-webgpu-133); reported real-world spread: "maxStorageBufferBindingSize varies from 128 MB on mobile GPUs to 4 GB on desktop discrete GPUs" — [ayoob.ai analysis](https://ayoob.ai/blog/webgpu-maxstoragebufferbindingsize-limits-enterprise)
- Native CUDA from Rust: cudarc provides a "minimal and safe api over the cuda toolkit" (host-side CUDA driver bindings) — [cudarc on crates.io](https://crates.io/crates/cudarc); the Rust-CUDA project was rebooted in 2025 and aims to interoperate with cudarc — [Rust-CUDA reboot blog (2025-01)](https://rust-gpu.github.io/blog/2025/01/27/rust-cuda-reboot), [update (2025-03)](https://rust-gpu.github.io/blog/2025/03/18/rust-cuda-update/); NVIDIA documents an official "CUDA Rust" path with kernels "written in Rust, compiled natively to PTX" — [NVIDIA developer blog](https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/)
- Ecosystem maturity signal: community threads asking "What is Rust-CUDA's Status?" indicate the GPU-Rust toolchain is usable but young — [r/rust thread](https://www.reddit.com/r/rust/comments/1ds2qgu/what_is_rustcudas_status/)

### Inferences
- Proposed portable explorer: Rust/Wasm for CPU numerics and wgpu for supported graphics/compute. Bundle size is unmeasured; WebGL2 fallback must not be assumed to preserve WebGPU compute functionality.
- Precision policy: keep a tested CPU/Wasm f64 path or native backend for sensitive calculations; evaluate f32 GPU error for each task instead of assuming every f32 result is qualitatively wrong. Double-float emulation is not automatically IEEE binary64-equivalent. This is a proposed validation policy, not evidence that any browser result is certified — [WebAssembly types](https://webassembly.github.io/spec/core/syntax/types.html), [WGSL floating-point rules](https://www.w3.org/TR/WGSL/#floating-point-evaluation).
- Transfer/deployment costs are qualitatively favorable (static hosting of a wasm bundle; wgpu publishes its examples online), but buffer-size defaults (256 MiB maxBufferSize / 128 MiB storage binding, requestable higher) bound how much landscape state can be uploaded; a hybrid design should stream compact precomputed fields rather than raw simulation state.
- Native Rust CUDA bindings alone do not supply a continuation/Floquet stack. Additional libraries, bindings or implementation work would need evaluation; this pass did not inventory Rust numerics sufficiently to claim every solver must be rebuilt.

### Gaps
- WGSL f64-emulation library maturity (double-float crates/techniques for WGSL) was not surveyed; only the open proposal and emulation discussion were sourced.
- wasm memory ceilings for the browser (wasm32 4 GiB address-space limit; memory64 shipping status across engines as of 2026-10) were not verified against primary sources this session.
- Concrete wgpu/wasm bundle sizes and first-load latency numbers were not sourced (no benchmark run; artemis and heavy jobs off-limits).
- Rust linear-algebra/solver crates for the explorer's client-side math (dense/sparse f64, eigenvalue, ODE integration in wasm) were not surveyed this session.
- cudarc's f64 support and maintenance cadence not verified beyond the crate description and 2025 project blogs.

## Key Question 4: All-in-one vs hybrid (reference research backend + portable browser explorer) — comparison, deployment/licensing/transfer, and how to decide without unsupported performance claims

### Takeaway
A native numerical backend with an independently shareable browser explorer is a reasonable design proposal, not the uniquely supported architecture. Compare it with Julia-generated static/interactively exported views and CPU/Wasm computation before committing to another implementation language. No head-to-head performance or integration-cost benchmark was run.

### Cited Findings
- Browser coverage is now sufficient to justify a browser-first explorer: WebGPU is stable in Chromium (desktop since 113, Linux NVIDIA since 147), Firefox (Windows/macOS), and Safari 26, with Firefox Linux/Android expected during 2026 — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- These are **GPU API**, not browser CPU, restrictions: WGSL lacks f64; WebGPU has per-buffer/binding limits, with higher supported limits requestable. CPU WebAssembly retains f64 — [WGSL](https://www.w3.org/TR/WGSL/#scalar-types), [WebGPU limits](https://www.w3.org/TR/webgpu/), [WebAssembly](https://webassembly.github.io/spec/core/syntax/types.html).
- Python browser compute is subset-only: Pyodide (CPython on wasm, no threading/multiprocessing, Python ≤ 3.13 as of 2026-03) with no JAX — [Pyodide docs](https://pyodide.org/en/stable/usage/wasm-constraints.html); [jax#1472](https://github.com/jax-ml/jax/issues/1472); [ericmjl blog](https://ericmjl.github.io/blog/2026/3/8/my-weekend-experiment-pymc-wasm/)
- The surveyed full Julia numerical stack is documented for native CPU/GPU execution, including continuation and periodic-orbit analysis; local native execution does not require a hosted service — [BifurcationKit docs](https://docs.sciml.ai/BifurcationKit/dev/); [hal-02902346](https://inria.hal.science/hal-02902346/).
- Rust/wgpu explorer licensing/deployment is verified permissive and static: dual Apache-2.0/MIT, wasm + WebGL2 fallback — [wgpu README](https://github.com/gfx-rs/wgpu)
- No public cross-stack benchmark comparing BifurcationKit vs AUTO-wrappers vs custom JAX/Rust continuation on the same problem was found in this pass; sparse-GPU linear algebra in JAX is reported as a practical bottleneck — [JAX-AMG (arXiv 2606.09001)](https://arxiv.org/html/2606.09001v1)

### Inferences
- Proposed architecture (not a measured ranking): a native reference backend, with Julia/BifurcationKit a well-documented candidate in this sample, plus a portable explorer consuming versioned branch/spectrum artifacts. The explorer could use CPU/Wasm f64 or tested GPU previews; compare this with Julia-generated static views. No exhaustive comparison established that BifurcationKit is the only stack covering the checklist.
- All-in-one trade-offs are workload-dependent: Julia can generate static views or serve live callbacks; Python may integrate several numerical libraries; Rust may need additional solver implementations or bindings. None of these observations establishes a causal productivity or performance ranking. Do not infer that every Julia artifact needs a server or that every Rust numerical component must be rewritten.
- Benchmark gates (controlled, reproducible; run locally, remote artemis excluded per constraint; every gate records hardware, versions, tolerances; no winner declared without these):
  1. Correctness/precision gate: f64 continuation results vs an independent reference (e.g., AUTO) — max parameter/state deviation along branches; JAX runs with and without x64 flag to quantify silent-f32 risk — motivated by [JAX x64 docs](https://docs.jax.dev/en/latest/101/default_dtypes.html).
  2. Continuation throughput gate: accepted continuation steps/second and Newton iterations/step on 2-3 canonical landscape models (small ODE, stiff ODE, discretized PDE ~10^5-10^6 unknowns) per stack.
  3. Sparse/matrix-free gate: Newton-Krylov iteration counts and memory for the PDE case, matrix-free vs sparse-Jacobian configurations; JAX sparse-GPU behavior compared against its documented bottleneck — [jax#8531](https://github.com/jax-ml/jax/discussions/8531).
  4. GPU f64 gate: measured f64 vs f32 kernel throughput on the available local GPU for the dominant kernels (Jacobian/monodromy products); no consumer-GPU f64 ratios assumed from vendor folklore.
  5. Explorer transfer gate: bundle download size, first-interactive latency, bytes uploaded per landscape view, and behavior at WebGPU default limits (256 MiB/128 MiB) vs requested higher limits — [Chrome blog 133](https://developer.chrome.com/blog/new-in-webgpu-133).
  6. Floquet/PO gate: periodic-orbit continuation and multiplier accuracy on a test problem with known multipliers, per stack that supports it (BK, AUTO; JAX/PyTorch only if assembled).
- Commitment-minimization heuristic consistent with the user's stated preferences: contract-first (artifact schema between backend and explorer), so the backend stack can change without touching the shareable UI, and any stack choice is reversible after the gates run.

### Gaps
- No head-to-head benchmark data exists in these notes: all speed/comparison claims are explicitly deferred to the gates above; nothing was executed, and the remote NVIDIA host (artemis) was deliberately not used.
- Licensing of BifurcationKit.jl, JAX, PyTorch, AUTO-07p and wrappers not verified against LICENSE files this session (wgpu's dual license is verified); confirm before distribution decisions.
- Julia (Pluto/Genie) and Python (FastAPI/panel-class) server-UI options were not verified against primary docs this session.
- Whether BifurcationKit is callable from Python via juliacall (a middle path for a Python shop) was not verified.
- Longitudinal maintenance/metrics (release cadence beyond version snapshots: BK v0.4.17 2026-10, PyTorch 2.14 docs 2026-05, wgpu v30, Optimistix Python ≥ 3.11) were not systematically assessed.
